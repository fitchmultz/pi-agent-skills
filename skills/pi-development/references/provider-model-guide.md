# Provider and Model Guide

Use for provider registration, auth, dynamic catalogs, model metadata, or SDK model-runtime work. Read installed `docs/providers.md`, `docs/custom-provider.md`, `docs/models.md`, and current pi-ai/Pi types first; read `docs/llama-cpp.md` for local llama.cpp workflows.

## Choose the smallest provider mechanism

1. Use `models.json` for endpoint/model configuration that needs no runtime code.
2. Use legacy `pi.registerProvider(id, config)` for supported APIs, static/simple dynamic catalogs, or legacy OAuth/`streamSimple` integration.
3. Use `pi.registerProvider(createProvider(...))` when the provider owns native auth, credential filtering, catalog caching, or stream behavior.
4. Hand-build a complete `Provider` only when `createProvider` cannot express the needed refresh/store semantics.

`models.json` composes above native providers. With legacy config, extension fields can win while `modelOverrides` still apply last; inspect the active composer for precedence-sensitive fields. Never spread provider ownership across extensions unless the merge/replace order is intentional and tested.

## Full provider extensions

- Import `createProvider`, auth helpers, and types from the `pi-ai` root. Root types do not export concrete API factories, despite the current native-provider docs; import factories such as `openAICompletionsApi` from `@earendil-works/pi-ai/compat`. Native npm supports `/api/*`, but Pi's Jiti aliases can misresolve subpaths. Qualify the real bundled loader and shipped module form; where needed, keep one explicit supported `/compat` factory. Native physical peers are not unconditionally replaced by Jiti mappings; see [Native extension module loading](runtime-authoring-guide.md#native-extension-module-loading). Do not build a custom resolver or rely on root globals masked by Jiti.
- A complete `Provider` owns `id`, `name`, auth, synchronous `getModels()`, optional `refreshModels`/`filterModels`, and both `stream` and `streamSimple`. Registering it discards any same-id legacy state and replaces any prior native provider; switching back deletes native ownership and starts a fresh legacy config. Only later legacy re-registrations merge defined fields.
- `createProvider({ models, fetchModels })` restores and persists the dynamic overlay through Pi's `ModelsStore`, preserves the prior list when fetching fails, supersedes/aborts older provider generations, and owns serialized generation-checked publication. Return fetched models; do not add manual publication code. A persistence failure prevents the paired in-memory update, so validate fetch and persistence failures separately. The callback receives the canonical credential/stored/publish/network/force/signal context.
- Dynamic providers need a static or stored baseline: interactive and RPC modes restore cached catalogs and then refresh in the background; print mode, `--list-models`, and default SDK construction do not automatically perform network refresh. `/model` and the model picker call `modelRuntime.refresh()`, which reloads `models.json` before catalog refresh.
- Handwritten `refreshModels` implementations read the immutable `context.stored` snapshot and publish persistence plus synchronous catalog mutation through `await context.publish({ persist, update })`. Never mutate first or use removed `context.store`. Omit `persist` to leave storage unchanged, pass a `ModelsStoreEntry` to write, or pass `null` to delete. Stop if publication returns `false` because a newer generation won.
- Honor `allowNetwork` and the concrete `signal`; treat `force` as an explicit freshness request. Cache-only recovery may pass `credential: undefined`. Config-form callbacks that only return models remain unchanged; only custom persistence uses `stored`/`publish`.
- `filterModels(models, credential)` filters after auth is considered configured, but receives the raw runtime credential-store result, including a runtime API-key override when present. Do not assume ambient/env credentials are materialized in that argument.
- Do not assume native provider-level `baseUrl` and `headers` are request defaults. Put `baseUrl`/static headers on each model or return headers from auth resolution, then inspect a real or stubbed request.
- Current streams receive `TranscriptContext`: read system prompts/tool declarations from messages using the current helpers, not old separate context fields. Emit well-formed event sequences, exactly one terminal event, observe abort, preserve metadata, accumulate text/thinking/tool-call deltas, and honor option callbacks. Prefer the bundled API factories over reimplementing a wire protocol.
- Stream tool-call arguments with pi-ai's `ToolCallArgumentsStream`: keep one per open block in a map keyed by the provider's block index, set `block.arguments = stream.append(delta)` for each delta, and finish with `Object.assign(block, stream.finish())`, which parses the complete text once and reports malformed input in `argumentsError`. A provider that resends the complete argument text calls `stream.replace(text)`, which returns the new `delta` and the partial `arguments`. Keep raw JSON text, provider indices and other stream state off the content blocks so they never reach partial messages or transcripts; do not re-parse accumulated `partialJson`. Both classes come from the `pi-ai` root; `StreamingJsonParser.append()` returns `JsonChange`s for other incremental JSON. Grammar (custom) tool input uses `appendGrammarToolInputJsonDelta()` from the `/api/constrained-sampling` subpath (see the loader note in `current-version-hazards.md`): it takes each new delta, and `closeGrammarToolInputJson()` closes the input at the end. See the official `custom-provider-anthropic` example.
- Set `usage.cost.totalFromProvider: true` only when `total` is the provider's billed amount; missing or `false` marks a catalog estimate. Set the assistant message's `responseModel` when the provider reports the concrete model behind the requested one. A device-code login can set `openBrowserOnConfirm: false` or `copyCodeOnConfirm: false` on `OAuthDeviceCodeInfo` to stop clients offering those actions (both default to `true`).
- `/reload` clears factory caches and reinitializes providers on both hosts. On a reload-capable path, removing or renaming conditional registration does not by itself prove the old live provider was pruned. Explicitly unregister it or rebuild the runtime when validating removal.

## Auth and model-runtime rules

- `ModelRuntime` is the canonical async model/auth facade. Create one runtime, pass it to `createAgentSession`, and inject a pi-ai `CredentialStore` such as `InMemoryCredentialStore` for isolated tests. Extension code still uses synchronous `ctx.modelRegistry`; await `modelRegistry.refresh()` before reads that depend on fresh dynamic catalogs.
- Use native model-runtime auth and the bundled Anthropic provider on both hosts; configured workload federation and header-only auth do not require a nonempty resolved API key. The fork's upgraded SDK integration preserves the Anthropic API-version header and ordinary `x-api-key` auth, with explicit OAuth/Copilot Bearer branches. Preserve case-insensitive explicit headers and null deletion markers. Keep the native credential-cache owner/fetch identity; an injected client owns its own headers/auth/cache and does not inherit bundled construction defaults. Do not copy resolved secrets, replace the SDK globally or invent a fork-only federation API.
- Extension model selectors and actions that must mirror the current session scope should read the read-only `ctx.scopedModels` snapshot. Use its models and optional thinking levels when non-empty; an empty array means `--models`/`enabledModels` did not constrain the session, so fall back to all available models.
- Current pi-ai root exports omit the removed singleton `getModel`/`getModels`/`getProviders`/`stream` API. New SDK code should use `createModels`/provider factories, and Pi extensions should prefer `ctx.modelRegistry` plus `pi.registerProvider`. Use `/compat` for old singleton migration and, until the export/loader mismatch is fixed, the concrete lazy API factories needed by full provider extensions.
- Never import removed pi-ai `/base` entrypoints. Type-check the actual package before trusting examples.
- Preserve credential precedence deliberately: explicit per-request API-key override → runtime API-key override → stored credential → configured legacy/models.json key or command → inherited/native ambient resolver. A stored credential owns the provider, so failed/unsupported stored auth does not silently fall back to environment auth. Read stored credentials directly only for one-off inspection; request auth comes from `ModelRuntime.getAuth()` or provider-owned auth.
- `pi auth check` preflights provider or model credentials from the CLI and can print the resolved credential via `--credentials`; treat that output as a secret and never capture it in logs, transcripts, or artifacts.
- `ModelRegistry.refresh(options?: ModelsRefreshOptions)` and `ModelRuntime.refresh()` return `ModelsRefreshResult`; inspect `aborted` and each provider error rather than treating a resolved promise as universal success.
- `setRuntimeApiKey(providerId, key, { signal })` and `removeRuntimeApiKey(providerId, { signal })` are async auth mutations. Await and handle `CredentialSynchronizationError`. They make cached/local state consistent but do not wait for remote freshness; call `refresh({ providers: [providerId], signal })` separately when required.
- `auth.json` provider entries may include provider-scoped `env`; Pi applies these for in-process provider resolution/streaming. Do not log or persist resolved values elsewhere.
- Prefer registry stream/complete dispatch, which resolves request-time auth: don't require/extract/echo a nonempty API key (OAuth/header-only/ambient auth can be keyless). Keep returned-error and setup-abort classification; auxiliary calls report top-level tool usage. When explicit auth inspection is required, `ModelRegistry.getApiKeyAndHeaders()` results carry `ProviderHeaders`, whose values are `string | null`. Preserve null deletion markers unchanged when passing headers to `ModelRuntime`/pi-ai request options; do not filter, stringify, or spread them into a `Record<string, string>` assumption.
- Config-form OAuth `refreshToken(credentials, signal: AbortSignal)` must accept the concrete signal and propagate it to refresh fetches, locks, sleeps, and polling.
- Env indirection is explicit: uppercase header/key values are literals unless prefixed with `$`; `${VAR}` and leading `!command` are supported where current config types/docs say so. `$$` and `$!` escape literal prefixes.
- Pi runs a `!command` value when it first needs it and caches the output. Official Pi keeps that value, including the empty result of a failed command, until the process exits: after a secret rotates, restart Pi, or have the SDK owner set the new key with `ModelRuntime.setRuntimeApiKey()`. On the fork, `AgentSession.reload()` (`/reload`, `ctx.reload()`) clears every cached command value. The fork also refreshes a stored `auth.json` API key of `!command` form when the provider answers HTTP 401 or 403 before any output: it runs the command once more and, when the resolved auth changed, sends the request one more time. A failed or empty command leaves the cached key in place. The refresh covers chat streams, deferred responses, image generation and classifier calls through `ModelRuntime`. It does not cover a request with an explicit `apiKey`, a runtime key override, or a provider with `ignoreStoredCredentials`. `ModelRuntime` sees the status only through the `fetch` and `onResponse` request options, so a custom stream gets the refresh only when it sends its HTTP request through `options.fetch` or reports the response through `options.onResponse`. One request can then call the provider's stream function twice, and `before_provider_headers`, `before_provider_request` and `after_provider_response` handlers run again for the second attempt: keep the work before the first stream event repeatable, and do not count one response for each request. Source: `src/core/{resolve-config-value,auth-storage,runtime-credentials,model-runtime,agent-session}.ts`.
- `envApiKeyAuth` checks stored API-key credentials before environment variables. Build keyless/ambient auth only with an explicit resolver that reports configuration truthfully.
- OpenRouter and Kimi Coding support both API-key env auth and `/login` OAuth (`Sign in with OpenRouter` mints a user-controlled key; `Sign in with Kimi Code` uses device auth with refresh). Prefer login flows for interactive setup.
- In non-interactive mode, fail closed when auth is missing; never prompt or invent fallback credentials.

## Model metadata and compatibility

- Current built-in chat API literals are `openai-completions`, `mistral-conversations`, `openai-responses`, `azure-openai-responses`, `openai-codex-responses`, `anthropic-messages`, `bedrock-converse-stream`, `google-generative-ai`, `google-vertex`, and `pi-messages`. `Api` also permits custom strings; use exact current types and a real stream implementation.
- Treat `api`, `reasoning`, `input`, `compat`, `thinkingLevelMap`, `contextWindow`, `maxTokens`, `cost`, and optional `cost.tiers` as runtime behavior. Never guess them from model names.
- Both hosts publish `schemas/models.schema.json` and require supplied `contextWindow`/`maxTokens` in definitions or overrides to be positive numbers, not zero-as-unlimited. Omit unknown optional limits or use verified values. Validation also enforces positive integer image dimensions/byte/count limits (JPEG quality 1–100) and positive supplied prompt-cache lifetimes.
- Thinking levels are `off`, `minimal`, `low`, `medium`, `high`, `xhigh`, and `max`, but generated catalogs expose only provider-verified effort levels and each model still has only its mapped subset. Query `getSupportedThinkingLevels(model)` in SDK code or RPC `get_available_thinking_levels` after model changes.
- Direct Kimi K3-family routes (`kimi-coding/k3`, `kimi-coding/k3.1-pro`, `moonshotai/kimi-k3`, `moonshotai/kimi-k3.1-pro` and their `moonshotai-cn` counterparts) expose `low`, `high`, and `max`. Kimi Coding (`https://api.kimi.com/coding/v1`) and Moonshot both use OpenAI Chat Completions with `thinkingFormat: "openai"`, `supportsReasoningEffort: true`, `requiresReasoningContentOnAssistantMessages: true`, and mid-conversation system/tool-addition support. Copy each route's base URL, auth and pricing from the active catalog; `models.json` base-URL overrides for `kimi-coding` include `/v1`.
- Qwen Token Plan registers `qwen-token-plan`, `qwen-token-plan-cn`, `qwen-token-plan-individual`, and `qwen-token-plan-individual-cn`. Both hosts prefer the matching per-plan variable before the shared regional fallback; use the [Qwen credential mapping](#qwen-credentials-and-catalogs). Model names do not imply thinking support: current `qwen3.8-max` maps `low`, `medium`, and `xhigh`, while explicitly rejecting `off`, `minimal`, `high`, and `max`. Verify current catalog metadata instead of freezing a count.
- Built-in catalogs also include `google` (`gemini-3.1-pro-preview`, `gemini-3-flash-preview`, `gemini-2.5-pro`, `gemini-2.5-flash` via `GEMINI_API_KEY`) and `minimax-cn`, plus `cloudflare-workers-ai` classifiers `@cf/cloudflare/clef`, `@cf/cloudflare/clef-omni` (also `cloudflare/clef-omni` on OpenRouter), and `@cf/cloudflare/clef-flash` with `["text", "image"]` input support in `models.classify`. Always inspect the active latest host's generated catalog for newer models and providers.
- Pi loads llama.cpp as a hidden built-in with default server port `9931` (explicit stored URLs and `LLAMA_BASE_URL` win). `/login llama.cpp` stores router URL/optional key; `/llama` manages loading. Discovery is live and non-persistent. Current selection includes loaded models, sleeping models, and autoloadable unloaded presets; do not restore a loaded-only filter from old guidance. On both hosts, llama.cpp decision classifiers send images to `/v1/systemone` when image input is reported. Read server-derived model limits and the current manager rather than adding a duplicate provider or shell mutation during discovery.
- Each `cost.tiers` item must define `inputTokensAbove` and all four rates. Pi selects the highest strictly exceeded threshold from request-wide input plus cache read/write; ordinary cache writes use tier `cacheWrite`, while `cacheWrite1h` uses twice tier input.
- Current OpenAI-compatible thinking formats are `openai`, `openrouter`, `deepseek`, `together`, `baseten`, `zai`, `qwen`, `chat-template`, `qwen-chat-template`, `string-thinking`, and `ant-ling`. Use `chatTemplateKwargs` for `chat-template` and `chatTemplateArgs` for `baseten`; do not rewrite request payloads ad hoc.
- Current session affinity uses `sessionAffinityFormat`: `openai`, `openai-nosession`, or `openrouter`. It does not disable `prompt_cache_key`; do not restore removed `sendSessionIdHeader` flags.
- `compat.promptCacheKeyMode` is `"auto"`, `"enabled"`, or `"disabled"`. For Completions, `auto` sends the cache key to OpenAI or a route with long retention enabled; `enabled` sends it whenever caching is active. Responses `auto` and `enabled` both send it when caching is active. `disabled` suppresses it. Inspect the endpoint before you set it.
- Ordinary Completions requests omit `tools` when no tools are active, even with tool history; the fork's full inline-change mode below can omit top-level definitions even when tools are active. Set `compat.requiresToolsWithToolHistory: true` only for a proxy that requires the empty array. `requiresNonNullAssistantContent` separately changes textless assistant replay from `null` to `""`. Do not add payload-rewriting hooks for behavior covered by these native flags.
- In `openai-completions`, `compat.supportsDeveloperRole` defaults to `true` only for `api.openai.com` on both hosts; all other hosts receive `system` unless `compat.supportsDeveloperRole` overrides it.
- Anthropic threads require a `sessionId` and caching. Both hosts default them on for any provider whose `baseUrl.includes("api.anthropic.com")` (not only provider ID `anthropic`); this substring test is not a hostname security check, and explicit `compat.supportsMessageThreads` wins. Let Pi own continuation and full-request fallback. On the fork, a request asking for or carrying a provider summary block sends no message thread. Auxiliary requests that repeat earlier input use `disableContinuation`, and standalone owners use `registerSessionResourceCleanup()` and `cleanupSessionResources(sessionId)` from `@earendil-works/pi-ai/session-resources`, passing the ID actually used in provider requests. A copied fork session can use an inherited cache identity rather than its own `AgentSession.sessionId`; managed disposal already performs that cleanup.
- `OpenAICompletionsOptions.toolChoice` is a stream option, not model `compat`. Preserve its typed union: `"auto"`, `"none"`, `"required"`, or a named function object.
- Tool `constrainedSampling` is model-gated: `json_schema` + `strict: "prefer"|"require"` needs `compat.supportsStrictMode`/`supportsStrictTools` on the active path; OpenAI Lark/regex grammar needs `compat.supportsOpenAIGrammarTools`. Prefer falls back; require fails closed; grammar falls back when unsupported. Distinguish the [shared schema conversion rules](#shared-provider-contracts) from the fork's retained Claude budgets.
- Enable deferred tools only with endpoint proof: Anthropic references require `supportsMidConvoSystemMessages` plus `supportsMidConvoToolChanges`, OpenAI Responses search requires `supportsToolSearch`, and compatible Kimi Chat Completions use `supportsMidConvoSystemMessages` plus `supportsMidConvoToolAdditions`. Keep that Kimi path additive; do not blanket-enable the fork's distinct [full Completions change mode](#source-verified-fork-provider-additions). Validate immediate next-turn definitions.

The [OpenAI latest-model guide](https://developers.openai.com/api/docs/guides/latest-model) describes vendor API capabilities, not automatic Pi support. Verify model/endpoint, transport, accepted reasoning parameters, and Pi serialization before adopting async tools, WebSocket steering, reasoning configuration updates, or cache controls. API-key, subscription, and proxy routes may differ. Preserve the host's selected model/effort; this skill must not create a second model router or blindly copy vendor request examples.

Optional tools use native deferred exposure with `tool_search` on both hosts; instruction groups no longer exist. Native tool_search, provider-native search and gateway composition have different contracts. Read `runtime-authoring-guide.md` before changing exposure or instruction gates; native codemode/deferred tools are callable even when inactive.

## Classifier discovery and dispatch

Classifier models are separate from chat models on both hosts; they do not appear in `/model`. Extensions use `ctx.modelRegistry.getAvailableOfType("classifier")` to discover models with configured credentials, select the explicitly configured provider/model, and call `ctx.modelRegistry.classify(model, { state, questions, images }, options)`. Codemode uses the corresponding `models.getAvailableOfType()` and `models.classify()` methods. Enable native codemode when that is the intended surface; extensions do not need it. Do not route a classifier through chat streaming or replace the selected chat model/runtime.

Pass JSON-compatible state and the shared choice, score or bool question shapes. Match image requirements to the selected classifier's actual `input` and route limits; a text-only classifier is not an image fallback. Inspect `result.stopReason` before consuming `result.answers`; an error/abort is not a negative classification. Preserve optional `result.usage`, including usage returned alongside a failure, and label catalog costs as estimates rather than provider billing. Extension-owned tool calls return that actual usage on the outer tool result; native codemode already aggregates it, so do not count it twice. Discovery/auth availability does not qualify a live request. See `docs/models.md` and `docs/codemode.md` for the shared types and setup.

Auxiliary registry classifier calls do not inherit the session chat request's hooks, HTTP idle timeout or retry settings. Extension/SDK owners pass a concrete cancellation signal and supported classifier options such as `timeoutMs` and `maxRetries`. For adapters using the shared HTTP classifier helper, including Google Decisions, that timeout is per HTTP attempt, not an overall deadline; inspect custom or chat-fallback adapters separately. That helper retries twice by default. See **Request retries on limit errors** under [Fork provider differences](#fork-provider-differences) for the retry-delay cap on both hosts and for the fork's immediate failure on quota, budget, billing or plan-limit errors. Native codemode supplies its script signal, not a third classifier-options argument. Keep the script deadline/cancellation boundary separate from a provider timeout.

Provider `headers` in `models.json` reach every model of the provider on both hosts, and `models` and `modelOverrides` change chat models only. On the fork, a provider's `classifierOverrides` sends `headers` with one classifier model by ID, in addition to the provider's headers and replacing one of the same name; values resolve like other `models.json` headers. A chat model with the same ID, such as `openai`'s `gpt-6-luna`, does not receive them. The fork's `docs/models.md#use-classifier-models` has an example: a Cloudflare AI Gateway header (`cf-aig-max-attempts`) that makes the gateway try each `gemini-decision-1` request once while Google's chat models keep the gateway's retries. On official Pi, an extension passes `headers` in the options of its own `ctx.modelRegistry.classify()` call. Codemode's `models.classify()` passes only its script signal on both hosts, so on official Pi a codemode call gets the provider's `models.json` headers but no classifier-specific ones.

### Fork Google Decisions

The fork adds the `google` provider's `gemini-decision-1` classifier with API `google-decisions` and text/image input. The adapter accepts either a resolved API key (sent as `x-goog-api-key`) or a configured credential header (`authorization` or `cf-aig-authorization` from `model.headers` or `options.headers`, such as for Cloudflare AI Gateway passthroughs). Native API-key auth can resolve `GEMINI_API_KEY` through normal request-time auth; by default the adapter sends `x-goog-api-key` to `POST /v1beta/decisions`, not the Google chat/Vertex protocol or Bearer auth. Keep the configured endpoint's versioned base URL. When hydrating a Google catalog from an older snapshot, the bundled helper adds the missing classifier without replacing an existing same-ID classifier entry.

The adapter rejects more than 3,600 images but forwards MIME/data unchanged: it does not enforce a MIME whitelist, resize images, or locally enforce request-byte/token limits. Google's chat catalog finalizer is not this classifier's input limit. Validate the intended formats and practical request limits against the exact service.

Use the shared classifier context and let the native adapter serialize JSON state, image parts and questions. It maps bool questions to Gemini's noul form, restores caller question IDs after safe wire-key mapping, and normalizes answers to Pi's shared result types. A missing, refused or malformed answer fails the result with empty answers; any already-parsed usage remains. Prefer native registry dispatch rather than hand-building the wire request or assuming a root or `/compat` factory export. Do not assume every image MIME type is accepted or treat the advertised token window/image capability as live service qualification.

Official Pi has neither this Google classifier catalog entry nor its adapter. Its complete native path is the same discovery/dispatch above with an explicitly selected, available classifier such as an authorized Jev, Clef or OpenAI Decisions route, verifying question/image support and that route's credential requirements. Do not silently substitute providers, rewrite Google chat models as classifiers, or import the fork-only adapter on official Pi. If Google Decisions itself is required, report that specific official-host blocker. Sources: `packages/ai/src/api/google-decisions.ts`, `packages/ai/src/api/google-decisions-catalog.ts`, `packages/ai/src/providers/google.ts`, and `packages/coding-agent/src/core/model-registry.ts` on the selected host. No live Gemini Decisions request was made by this refresh.

### Fork Cloudflare AI Gateway GPT-6 Luna

The fork's `cloudflare-ai-gateway` provider lists OpenAI's `gpt-6-luna` classifier (API `openai-decisions`): the same catalog entry as `openai`'s, at the gateway's `/openai` passthrough. It needs the gateway's `CLOUDFLARE_API_KEY`, `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_GATEWAY_ID`. The token goes only in the `cf-aig-authorization` header, so the model stays available while `openai` uses Sign in with ChatGPT. The gateway itself needs access to OpenAI; see `docs/providers.md#cloudflare-ai-gateway`. Fork builds hydrated from an older pinned catalog snapshot derive the entry from that snapshot's `openai` entry.

For this route, the fork's shared classifier helper (used by OpenAI Decisions, System One, and Google Decisions) accepts an `authorization` or `cf-aig-authorization` header from `model.headers` or `options.headers` in place of an API key, as the OpenAI chat APIs already do. Official Pi has no gateway Luna entry, and its OpenAI Decisions and System One requests need an API key (`No API key for provider`). Its complete path is `openai`'s `gpt-6-luna` with `OPENAI_API_KEY` while `openai` is not logged in through `/login`, or another explicitly selected available classifier; see `docs/models.md#use-classifier-models`. Sources: `packages/ai/src/api/{classifier-shared,cloudflare,google-decisions}.ts`, `packages/ai/src/providers/{cloudflare-ai-gateway,cloudflare-auth}.ts` and `packages/ai/src/utils/headers.ts`. No live gateway request was made by this refresh.

## Shared provider contracts

Both official Pi `1.6.0` and the fork implement these provider contracts. Always inspect the effective generated/fetched catalog on the active host rather than freezing counts.

### GPT-6.2 model maps and defaults

Both hosts ship exact `gpt-6.2-astra` and `gpt-6.2-sol` entries with Sol fallback defaults on `openai`, `azure`, and `openai-codex`. (Cloudflare `/openai` synthesis remains fork-only below.) Saved/scoped selections still win; do not migrate the user's chosen model or build another router.

Frozen catalog rules prescribe 128,000 output tokens for both models, with route-specific context and logical thinking:

| Route | Context | Logical levels |
| --- | --- | --- |
| OpenAI Responses | 272,000 for both | `low`, `medium`, `high`, `xhigh`, `max`; no `off` or `minimal` |
| Azure Responses | 1,050,000 for both | The same five levels |
| Codex Responses | Astra 272,000; Sol 500,000 | The same five plus `minimal` mapped to wire `low`; no `off` |

Query the effective generated/fetched model and `getSupportedThinkingLevels()` rather than inferring a count, parser acceptance, or route parity. OpenAI's finalizer enables search, additional tools, positional system messages, and mid-conversation effort; its configuration-update effort path excludes ChatGPT sign-in. Azure clones pre-finalizer metadata and does not acquire those flags merely by sharing the family, so Azure serializes ordinary reasoning effort. On both hosts, Codex places the leading system prompt inside `input` (`developer` for reasoning models unless developer-role support is explicitly false, otherwise `system`) while omitting top-level `instructions`, enables `compat.supportsMidConvoEffort` (`configuration_update`, including mapping `off` to `"none"`) for GPT-6 models, sends `max_output_tokens` unless `compat.supportsMaxOutputTokens: false`, rotates cached WebSockets after 45 minutes, and retries once on a fresh connection after a 60-minute lifetime error. Thinking-suffix grammar is unchanged: a service tier is not a thinking suffix.

Base estimates in USD per million input/cache-read/cache-write/output tokens are Astra 8/0.4/10/40 and Sol 2/0.1/2.5/10. The existing request-wide tier strictly above 272,000 input plus cache-read/write tokens multiplies the first three rates by 2 and output by 1.5. These are catalog estimates, not invoices.

Inspect the effective exact provider/model on the active host first. When adding or overriding custom entries in `models.json`, supply verified maps, positive limits, rates, and route-supported compat; vendor parameter advice does not automatically filter unsupported optional parameters. Sources: `packages/ai/catalog/{families/openai,providers/openai,providers/azure,providers/openai-codex}.ts`, `src/core/model-resolver.ts`, and the selected Responses adapters.

## Validation and safety

- Validate registration with `--list-models`, auth configured/unconfigured states, thinking-level enumeration, and one real or stubbed stream for each custom request path.
- For dynamic catalogs, test cached/offline startup, successful refresh, fetch-failure retention, persistence-failure non-publication, abort, stale-generation suppression, forced refresh, and the actual mode that should trigger network work.
- For llama.cpp, validate unloaded, loaded, server-down, abort/timeout, and reload states without publishing images or copying credentials into artifacts. Treat download and load/unload as explicit local mutations; do not perform them during read-only inspection.
- For remote model smokes, inject only the needed credential into the model-only process, avoid package/lifecycle scripts, use `-p` with `--no-session`, set a verified thinking level, and save separate non-secret artifacts.
